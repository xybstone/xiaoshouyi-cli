实测中修复和确认的规则：

- description 的162字段内容相同但顺序变化，曾导致发送前误报 PLAN_STALE。现在稳定排序计算指纹，真正的字段约束变化仍会阻断。
- 通用输出现兼容字符串 code="200" 和 data envelope，不再丢失描述结果。
- 执行只有回读通过才退出0；拒绝/未落地为1，结果不确定为2，待验证为3。非标准业务错误保存脱敏的 HTTP 状态、业务码和短消息，不保存原始响应或认证头。
- 服务器要求至少一条工时，以及问题原因、报告正文。工时字段标签为“耗时/h”，当前业务要求0.5步长；本次契约复用 fields.timeSheet__c.enum 发送前校验，不推广至其他环境或业务类型。
- 0.16小时取得明确1002001校验拒绝；0.69小时首次原响应未保存。前后关联查询总数均为0，结合步长规则完成本地未落地审核；首次证据缺失边界保留，没有补造错误码或修改旧计划。
- 首次 resolve 计划错误期望节点处理后立即得到状态9，实际为阶段3/状态3；旧账本保留 applied_pending_verification 的失败断言，没有改成成功或重发 agree。节点推进和最终已解决/流程关闭分别验证。
- 增加可选 recordPreconditions，将本次 submit 限于阶段1/状态1，将结单和内容补录限于已核验的阶段3/状态3；已结束工单不能再用旧语义生成新提交计划。原错误 resolve 映射在当前配置中改为 unverified，旧计划及失败断言保持原样。
