## 需要明确补齐的事项

### G1：真实动作契约与写权限（阻断 P3/P4）

`skill/references/tickets/contracts.unverified.json` 的 18 个动作均为 unverified，历史和下载也未核验。`src/tickets/actions.ts:144` 在此状态返回 blocked；默认能力报告中的 executable 为 false。这是当前正确的行为，也是尚未交付真实业务操作的直接证据。

需逐个从官方文档或页面只读获取动作、表单和权限读取协议，记录业务类型、角色、状态、payload 和返回语义。对象 createable/updateable、disabled 标记及状态枚举仍不能替代这些证据。业务类型列表与历史记录不匹配的问题也未关闭。

### G2：不确定结果只能保留，尚不能自动恢复（P2 功能缺口）

`src/tickets/actions.ts:333` 的 reconcile 只在已有 submission 时继续验证。没有回执时，outcome_unknown 直接返回原状态；dispatching 只被表示为 outcome_unknown，没有关联查询。这覆盖“禁止盲目重发”，没有覆盖“识别请求实际是否落地”。

复现场景：服务器已完成分派，但连接在返回回执前断开。账本保存 outcome_unknown，之后回查不会通过工单或关联历史确认分派结果。创建超时且没有返回 ID 时，也没有按已核验唯一业务关联条件定位新记录的机制。

需补充每动作的只读恢复契约：已知目标如何查询历史/业务关联，创建如何使用真实唯一关联条件，多候选/无匹配如何继续保持不确定，如何记录人工核对结论。不能仅因主表当前值相同就证明是本次操作造成，也不能靠相似标题认定创建成功。若服务端没有可靠关联条件，应明确保留人工恢复边界。

现有测试验证了“不重发”和“已有回执后回读恢复”，并未验证“无回执但已落地”的结果识别。

### G3：查询目标尚未全部产品化（P1 缺口）

`src/services/ticket.service.ts:75` 对没有登记映射的编号筛选返回 UNVERIFIED；时间字段及 unix-ms 编码也要求生产 read 契约。随附配置没有 read 项，不能因为参数存在就称已支持按编号或时间查询。

客户、负责人筛选目前接收明确 ID，没有工单专用的名称解析/多候选选择流程。客户上下文有按需读取代码；资产上下文明确为 unverified。需要以真实字段、引用及权限完成这些剩余读取验收。

本次 CLI/MCP 的 REST 状态筛选实测通过。先前原 NeoCRM BFF 聚合的一个 IN 条件被业务拒绝，不能据此推断 REST 工单筛选不可用，也不能在两种接口间直接沿用未经验证的语法。

### G4：引用、人员与业务类型解析尚未实现完整业务流程（P3 缺口）

目前动作参数依靠已登记字段和明确输入，没有工单专用的候选处理人、客户、派工池、部门解析服务，也没有同名消歧、池内成员与角色校验。分派所需的 ownerId/responsibleTE__c/assigner/池的联动规则尚无真实契约。

取得接口后可继续调用现有查询/元数据能力补少量领域解析逻辑，不需要新建一套身份或 HTTP 系统。

### G5：远端时间线与关键副作用尚未验收（P3/P4 缺口）

`src/services/ticket.service.ts:260` 在没有已核验历史来源时返回 UNVERIFIED；本地账本不是远端完整审计历史。处理记录的追加承载对象、内外部回复可见性、参与人和前后状态等仍需真实证据。

`backend.verify` 可以检查主表及额外关联记录，但现在没有生产检查配置，不能证明 SLA、报告、评价、通知或外部系统已同步。时间线目前按来源返回、来源内按 ID 排序；统一事件时间及跨来源排序也尚未核验。

### G6：现有会话复用仅交付了只读 CLI 入口（运行接入待补）

`scripts/with-neocrm-session.mjs` 启动时调用原库获取有效 Token，随后仅在当前进程注入 XSY_ACCESS_TOKEN，并强制关闭写入。它不持续提供 Token，也不是可执行生产动作的认证桥。

`src/auth/manager.ts:47` 对 env Token 直接取值，不使用其他账号的存储凭据续期；这是正确的隔离行为。若选择 NeoCRM 作为长期 CLI/MCP 凭据来源，应通过同一原认证库增加持续供给/刷新能力，并补服务端租户和账号核验。使用 CRM Cookie 的动作还需分别验证 Cookie 身份一致性，不能从 OAuth 读取成功推断。

本项目原有自身登录/刷新路径继续可复用，不要求永久迁移或复制 NeoCRM 凭据。MCP 宿主签名校验已实现，但可信宿主实际产生确认、签发和调用执行的流程还需验收。

## 补齐顺序与验收出口

1. 完成剩余只读事实：编号/时间、业务类型与创建表单、引用/候选人员、当前允许动作和历史/关联协议。此阶段继续只读，不用试写探索接口。
2. 修补 P2 无回执恢复；补“服务器成功但回执丢失”“多候选不能判定”“进程中断后只读恢复”等有意义的契约测试。核实服务端真实并发/幂等能力；没有则继续明确 best_effort 和本地单计划保障范围。
3. 逐个登记核心真实动作，补字段/引用解析、真实脱敏响应契约及必要适配。不能假设只填 JSON 配置就能覆盖尚未知的表单或上传协议。
4. 核对具体测试环境或测试目标、字段、范围和最终 payload 的授权后，在同一条测试工单执行创建→分派→追加处理记录→解决→必要中间动作→关闭，每步回读主表、历史和必要副作用。用户的开发和只读测试授权不包含任意生产工单写入；具体写入确认要求来自原 NeoCRM 项目 AGENTS.md 及其 neocrm-cli-safe 规范。
5. 按每个实际业务类型和角色验收，再逐条验收 P4；将权限拒绝、条件必填、非法动作、超时、并发、附件关联失败等列入真实契约/测试记录。

只有以上对应范围验收通过后，才能把其状态从“框架支持”改为“该业务类型的该动作已接入”。
